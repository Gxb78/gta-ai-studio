## Phase 0.8.4 : Prefetch Automatique

### Implémentation

**Backend** :
- Ajout du champ `origin: "user" | "prefetch"` dans `ClipPreviewRequest`
- Méthode `_prefetch_adjacent_clips()` dans `service.py`
- Logique non-récursive : seules les requêtes `origin="user"` déclenchent prefetch
- Fire-and-forget : les erreurs de prefetch ne propagent pas
- Toujours en `draft` profile pour économiser ressources

**Frontend** :
- Ajout du champ `origin?: "user" | "prefetch"` dans `ClipPreviewRequest` (TypeScript)
- Requêtes utilisateur incluent `origin: "user"` par défaut
- Pas de changement UI nécessaire (transparent)

### Comportement

Quand l'utilisateur clique "RENDRE L'APERÇU" sur un clip :
1. Le clip demandé est rendu avec le profile choisi (draft/fidelity)
2. En arrière-plan, les clips adjacent (précédent et suivant) sont prefetchés en draft
3. Le prefetch est non-récursif : `origin="prefetch"` ne déclenche pas d'autres prefetch
4. Si le cache hit, pas de nouveau job enfilé
5. Les erreurs de prefetch sont loggées mais ne bloquent pas la requête principale

**Cas limites** :
- Premier clip : prefetch seulement le suivant
- Dernier clip : prefetch seulement le précédent
- Clip unique : pas de prefetch

### Tests

Fichier : `services/api/tests/unit/test_preview_prefetch.py`

**Cas testés** :
- `test_prefetch_adjacent_clips_no_recursion` : Vérifie non-récursion

- `test_prefetch_uses_draft_profile` : Toujours draft même si user demande fidelity
- `test_prefetch_fire_and_forget` : Erreurs ne propagent pas

### Logging Structuré

**Format** : JSON Lines (jsonl), rotation 10MB, 5 backups

**Events loggés** :

1. **preview.request.received** (INFO)
   - Attributs : `clip_id`, `render_profile`, `timeline_revision`, `origin`, `has_window`
   - Déclenché : Début de `start_clip_preview()`

2. **preview.cache.hit** (INFO)
   - Attributs : `cache_key`, `clip_id`, `hit_count`
   - Déclenché : Cache hit sur entry ready

3. **preview.cache.hit_inprogress** (INFO)
   - Attributs : `cache_key`, `clip_id`, `status`, `job_run_id`
   - Déclenché : Cache hit sur entry pending/rendering

4. **preview.cache.miss** (INFO)
   - Attributs : `cache_key`, `clip_id`, `render_profile`, `origin`
   - Déclenché : Nouveau job enfilé

5. **preview.prefetch.start** (INFO)
   - Attributs : `current_clip_id`, `current_index`, `adjacent_count`
   - Déclenché : Début du prefetch

6. **preview.prefetch.completed** (DEBUG)
   - Attributs : `adjacent_clip_id`, `adjacent_index`, `cache_hit`
   - Déclenché : Prefetch réussi

7. **preview.prefetch.failed** (WARNING)
   - Attributs : `adjacent_clip_id`, `adjacent_index`, `error`
   - Déclenché : Erreur prefetch

**Exemple de log** :
```json
{
  "schema_version": "1.0",
  "timestamp": "2026-07-22T15:30:45.123Z",
  "level": "INFO",
  "event": "preview.cache.hit",
  "service": "api",
  "message": "Preview cache hit (ready)",
  "project_id": "proj-123",
  "attributes": {
    "cache_key": "abc123def456...",
    "clip_id": "clip-789",
    "hit_count": 12
  }
}
```

### Méthodes Repository

**`get_preview_cache_stats()`** :
- Compte total entries par statut
- Calcule cache hit rate
- Récupère top 10 entries by hit_count
- Moyenne ref_count et total bytes

**`get_preview_render_metrics()`** :

## Décisions Techniques

### 1. Prefetch en draft uniquement
**Raison** : Économiser CPU/stockage. L'utilisateur peut toujours demander fidelity explicitement.

**Trade-off** : Si l'utilisateur navigue avec fidelity, les clips adjacents seront en draft jusqu'à demande explicite.

**Alternative rejetée** : Hériter du profile de la requête user → risque de surcharger la queue.

### 2. Fire-and-forget pour prefetch
**Raison** : Les erreurs de prefetch ne doivent jamais bloquer la requête principale.

**Implémentation** : `try/except` dans la boucle, log warning, continue.

**Alternative rejetée** : Propager les erreurs → casse l'UX si clip adjacent invalide.

### 3. Cache hit rate = hits / (hits + ready_count)
**Raison** : Approximation rapide sans tracking des misses explicites.

**Formule** : `total_hits / (total_hits + ready_count)`

**Limitation** : Sous-estime légèrement le hit rate réel (ne compte pas les hits sur entries pending/rendering).

**Alternative rejetée** : Counter dédié pour misses → overhead supplémentaire.

### 4. Metrics sur 7 jours glissants
**Raison** : Balance entre pertinence et performance de la query.

**Query** : `WHERE job_type = 'RENDER_CLIP_PREVIEW' AND created_at > datetime('now', '-7 days')`

**Trade-off** : Les métriques anciennes sont oubliées. Pour historique long terme, ajouter agrégations quotidiennes.

## Impact et Bénéfices

### Prefetch Automatique
- **UX** : Navigation fluide entre clips, preview déjà prête
- **Cache hit rate attendu** : +30-50% (clips adjacents souvent consultés)
- **Overhead** : ~2 jobs supplémentaires par requête user (draft, 2-3s chacun)

### Observabilité
- **Debugging** : Logs structurés permettent de tracer chaque requête avec trace_id
- **Monitoring** : Dashboards possibles sur cache hit rate, durées de rendu
- **Alerting** : Possible de déclencher alertes sur `failed_count` élevé ou `avg_duration_ms` anormale

### Cache Global
- **Réutilisation cross-project** : Même source + même transform = cache hit
- **Économie ressources** : Évite re-rendu identique
- **Garbage collection** : LRU eviction automatique sur quota
